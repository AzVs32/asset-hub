# asset-hub 错误处理规范

## 0. 适用范围与规则强度

- 适用于错误类型、`Result` 返回值、错误转换、错误展示和错误日志相关的设计、实现、评审与测试。
- 本文档是本项目错误处理规则的唯一规范来源。其他文档应引用本文，不重复维护规则；实际错误码以代码中的元数据为准。
- 本文采用 Rust 通用错误处理机制，同时规定本项目的架构与展示契约。`AppError` 的形式、分类集合、HTTP 响应结构和 CLI 退出码是项目约定，不宣称为所有 Rust 项目的通用标准。
- **必须 / 禁止**表示强制规则；**默认 / 建议**表示通常采用的方案，有明确理由时可偏离并在代码或设计说明中记录；**可以**表示可选方案。
- 规范缺失或冲突时，按 `AGENTS.md` 报告具体位置与内容，不自行补造规则。得到修改规范的明确授权后，应同步修正相关示例、检查清单和测试要求。
- 示例中的 `<Module>`、`<Entity>` 是占位符。示例展示契约形状，不指定实际模块路径。

## 1. 目标

- 调用方能按失败语义决定处理方式，不依赖错误文案或第三方库细节。
- HTTP / CLI / TUI 共享应用错误的分类与错误码，各自负责协议和展示。
- 用户文案与内部诊断分离；在脱敏前提下保留足够的排查信息和原因链。
- 模块通过公开接口契约交互，更换基础设施实现不改变业务错误契约。
- 新增错误能够通过类型检查、元数据检查和行为测试落实规范。

## 2. 分层与职责

| 层 | 错误相关职责 |
|---|---|
| 入口适配器 | 将应用出口的 `AppError` 映射为协议或界面结果，建立或继承追踪上下文，在责任边界记录失败 |
| 应用层 | 编排用例，将模块或应用自身的失败转换为 `AppError`，选择安全文案，补充诊断上下文 |
| 业务模块 / 领域接口 | 定义操作错误及局部解析、校验错误；对需要应用分类的操作错误实现 `ClassifiedError` |
| 基础设施实现 | 实现领域接口，将第三方失败转换为接口约定的语义错误，并保留诊断原因 |
| 内核 / 共享契约 | 定义 `ErrorKind`、错误描述符和 `ClassifiedError` 等最小契约，以及内核自身的错误；不聚合业务模块的错误变体 |

这里的层次表示职责，不能据表格顺序推导所有代码依赖。必须遵守：

- 领域接口及业务错误不得依赖具体数据库、网络客户端等基础设施实现。
- 基础设施实现依赖其实现的领域接口；入口适配器依赖应用接口。
- 下层错误不得包含 `AppError` 或其他上层展示类型。
- 跨模块依赖限于公开接口契约，不依赖对方内部错误表示。

## 3. 错误类型与表示

| 类型 | 适用情况 |
|---|---|
| enum | 需要公开可区分的失败原因，调用方据变体处理 |
| struct | 只有一种失败，或通过访问方法公开稳定信息而隐藏内部表示 |
| struct 包私有 enum | 内部原因较多，但不希望变体成为公共 API |

规则：

- 公共错误必须实现 `Debug`、`Display` 和 `std::error::Error`；默认使用 `thiserror`，必要时可以手写等价实现。
- 需要跨线程传递或进入统一应用错误载体的操作错误必须满足 `Send + Sync + 'static`。
- enum 是否使用 `#[non_exhaustive]`，必须根据版本兼容性目标选择，不对所有公共 enum 一律添加。
- 可独立演进的模块错误 enum 默认使用 `#[non_exhaustive]`；模块自身的映射实现必须穷尽匹配，外部调用方必须处理未知变体。
- 本项目的 `ErrorKind` 采用穷尽 enum，原因见第 5 节。
- 业务信息使用结构化字段；诊断上下文可以是字符串，但不得用拼接文案代替可识别的错误语义。
- 根据实际体积或 lint 提示对较大的载荷装箱，不为每个错误强制引入堆分配。
- `Display`、`Debug`、`source()` 和第三方错误文案均属于诊断接口，默认不保证适合直接展示给用户。

## 4. anyhow、诊断封装与 AppError

| 类型 | 职责 | 使用位置 |
|---|---|---|
| `anyhow::Error` | 类型擦除、保留原因链和诊断上下文 | 私有实现、字段私有的诊断封装内部、入口内部、测试 |
| 自有诊断封装 | 隐藏原因载体的具体库，同时提供标准原因链 | 操作错误的原因字段、`AppError` 的私有原因字段 |
| `AppError` | 应用出口契约：分类、稳定错误码、安全文案与诊断关联 | 应用出口、入口适配器的应用错误映射 |

本文以 `Diagnostic` 代指项目自有的诊断封装：字段私有，实现 `Error + Send + Sync + 'static`，通过 `source()` 保留底层原因。内部可以使用 `anyhow`；公共字段、构造函数和转换签名不得要求调用方使用 `anyhow`。

数据流向：

```text
基础设施失败
  → 基础设施边界转换为接口约定的操作错误，保留原因
  → 应用层保留分类与错误码，选择安全文案，形成 AppError
  → 入口适配器映射为协议 / 界面结果，记录脱敏后的诊断
```

- 业务模块和应用用例的公共操作 API 必须返回有明确语义的错误类型，禁止用 `anyhow::Result` 替代其错误契约。
- 私有函数可以使用 `anyhow::Result`，但不得因此丢失公共操作所需的分类和结构化信息。
- 需要跨边界保留诊断的操作失败，必须保留类型化原因，不得仅调用 `to_string()` 后丢弃原错误。局部校验错误可以按契约收敛为稳定的结构化原因，不强制携带底层解析库错误。
- 局部解析和校验错误可以保持小型 struct / enum，不需要先包装进通用诊断载体。

## 5. 内核分类契约

分类表示失败语义，不表示日志严重程度或重试许可：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ErrorKind {
    InvalidInput,      // 输入不符合当前操作的契约
    Unauthenticated,   // 缺少有效认证
    PermissionDenied,  // 当前主体不允许执行操作
    NotFound,          // 当前操作要求存在的资源不存在
    Conflict,          // 与已有状态冲突
    Unavailable,       // 依赖暂时无法提供所需服务，不保证可安全重试
    Internal,          // 内部不变量失败或无法合理归类的内部失败
}

pub struct ErrorDescriptor {
    pub code: &'static str,
    pub kind: ErrorKind,
}

/// 需要转换为应用错误的操作错误实现此接口。
pub trait ClassifiedError: std::error::Error + Send + Sync + 'static {
    fn descriptor(&self) -> &'static ErrorDescriptor;

    fn kind(&self) -> ErrorKind {
        self.descriptor().kind
    }

    fn code(&self) -> &'static str {
        self.descriptor().code
    }
}
```

- `ErrorKind` 不使用 `#[non_exhaustive]`。项目选择让新增分类推动所有入口适配器同步更新，并以跨 crate 的穷尽匹配检查遗漏。
- 新增分类属于规范及公共契约变更，必须同步更新本文、适配器映射和相关测试；独立发布的依赖方应按兼容性策略升级。
- `descriptor()` 是分类和错误码的共同来源，不另行重写 `kind()` / `code()` 维护第二套映射。
- 不要求每个值对象错误、辅助函数错误或第三方错误实现 `ClassifiedError`。
- 分类应按当前操作语义判断，不机械照搬第三方状态码。例如“目标资源不存在”与“运行所需配置丢失”不一定具有相同分类。
- 取消、限流、超时等失败应按已有类别的明确语义处理；若需要独立处理而当前类别不适用，必须提出分类契约变更，不能为避免修改规范而一律塞进 `Internal`。

## 6. 模块错误规范

错误类型放在所属模块的 `error.rs`，区分两类职责：

- **操作错误**：作为模块或领域接口的失败契约；需要进入应用分类的类型实现 `ClassifiedError`。
- **局部错误**：用于解析、值对象构造或校验；可以是小型 struct / enum，由操作边界按语义转换，不强制提供 `Internal`、全局错误码或分类接口。

以下为需要表达业务与基础设施失败的操作错误示例，其中 `Diagnostic` 是第 4 节的自有封装；不要求每个错误具有全部变体：

```rust
#[derive(Debug, thiserror::Error)]
#[non_exhaustive]
pub enum <Module>Error {
    #[error("<entity> {0} not found")]
    NotFound(<Entity>Id),

    #[error("<module> dependency unavailable")]
    Unavailable(#[source] Diagnostic),

    #[error("<module> internal failure")]
    Internal(#[source] Diagnostic),
}
```

- 按失败语义分类。可以识别为不可用、冲突等原因的失败必须保留相应语义，不因暂时没有专门展示需求而改成 `Internal`。
- 新增细分变体或错误码，应有处理、诊断或对外契约上的需要。同一分类内不必为每种第三方报错增加变体。
- 只有操作确实可能产生未知内部失败时，才提供 `Internal` 兜底；纯解析、校验错误不要求包含该变体。
- 操作错误 enum 所在 crate 内的 `descriptor()` 必须穷尽匹配所有变体，不使用通配分支掩盖新增原因。
- 原因载荷不决定分类：包含诊断原因的 `Unavailable` 仍然是 `Unavailable`。
- 模块公共 API 可以返回所属局部错误或其实现接口约定的错误，不要求所有函数返回同一个模块级 enum。

### 基础设施错误转换

- 仓储等接口由领域接口所属方定义失败契约，实现位于基础设施层。
- 基础设施层将可识别的第三方失败转换为相应语义；确实无法合理分类的内部失败才归入 `Internal`。保留可用于诊断的底层原因。
- “没有查到记录”是否是失败取决于接口契约：可选查询通常返回 `Result<Option<T>, E>`，要求目标存在的操作可以返回 `NotFound`。
- 公共错误的字段、变体载荷、构造函数和转换实现，不得暴露可替换的具体数据库、网络客户端等实现库类型；改写 `#[from]` 为手写 `From` 并不能消除这种耦合。
- `#[from]` 可以用于项目自有契约类型，以及明确作为接口契约使用的标准库或其他稳定类型。不得用它自动抹去需要按操作上下文判断的语义差别。

## 7. AppError 规范

`AppError` 定义在应用层，默认采用字段私有的 struct，实现 `Error + Send + Sync + 'static`，通过访问方法提供以下信息：

| 信息 | 契约 |
|---|---|
| `kind` | 用于入口映射的 `ErrorKind` |
| `code` | 来源于错误描述符的稳定错误码 |
| `message` | 明确选择的用户安全文案；不得直接采用诊断格式输出 |
| `source` | 私有诊断原因；存在原因时通过 `Error::source()` 保留原因链 |
| `trace_id` | 可选的关联标识，由入口追踪上下文提供或继承 |

### 转换与安全文案

- 通用转换函数可以接收 `ClassifiedError` 和显式提供的安全文案：先读取描述符，再保存原错误为原因。各具体转换可以复用这些步骤，不强制编写泛型 `From<E>` 实现。
- 安全文案由应用层根据错误码及允许公开的参数选择。需要插值时，只使用经明确允许披露的结构化字段；不能用 `Display`、`Debug` 或完整原因链代替。
- `Internal` 必须覆盖为通用安全文案；无法选择可信文案时，其他分类也必须采用安全兜底文案，并保留原分类与错误码。
- 用户提供且允许披露的路径等信息可以按展示策略使用；内部路径、SQL、凭据、堆栈、内部主机名等不得未经审查进入用户文案。
- 应用自身的前置条件或编排失败应有自己的错误描述符，不为统一转换而伪装成某个下层模块的 `Internal`。
- 错误响应使用专门的展示结构，只选取允许公开的信息，不直接序列化整个 `AppError`。

### 上下文与追踪

- 补充诊断上下文不得改变 `kind`、`code` 或原有失败语义。可以在 `AppError` 的私有原因上使用 `anyhow::Context` 或等价机制；不得将所有附加上下文的失败统一改成 `Internal`。
- 根据用例语义确实需要重新分类时，必须显式转换并保留原原因，说明转换理由。
- 纯错误转换不生成新的 `trace_id`。入口建立或继承关联标识，通过调用上下文传递；同一次请求或用例沿用同一关联标识。

## 8. 适配器映射规范

- 应用错误的展示和协议映射只依赖 `AppError` 的公开契约，不匹配模块错误，也不解析第三方诊断原因。
- 适配器必须穷尽匹配 `ErrorKind`，不使用通配分支；新增分类必须导致未更新的映射编译失败。
- 入口自身的协议失败，例如不支持的 HTTP 方法，可以按协议处理，不必制造模块错误；需要进入统一应用错误展示时应显式转换。
- 下表规定本项目应用错误的默认映射。协议要求、安全策略或公开 API 的特殊约定需要不同映射时，必须在对应接口文档中说明并测试，不能通过检查内部原因临时决定。

### HTTP

| ErrorKind | 默认 HTTP 状态码 |
|---|---|
| InvalidInput | 400 |
| Unauthenticated | 401 |
| PermissionDenied | 403 |
| NotFound | 404 |
| Conflict | 409 |
| Unavailable | 503 |
| Internal | 500 |

- 本项目默认响应体为 `{ "code", "message", "trace_id" }`；`trace_id` 不存在时为 `null`。`Internal` 仍保留 `code`，但 `message` 必须为通用安全文案，不输出原因链。
- 401 响应必须按认证方案提供 `WWW-Authenticate`。503 可以在存在可信等待时间时提供 `Retry-After`，但不能据此保证写操作可以安全重试。
- 该 JSON 结构是项目协议。若采用 RFC 9457 Problem Details，必须明确字段映射及兼容性安排，不把两种结构当作同一协议。
- 身份或资源存在性需要隐藏时，遵守已明确的安全策略，并对状态码及文案一起测试。

### CLI

| ErrorKind | 默认退出码 |
|---|---|
| Internal | 1 |
| InvalidInput | 2 |
| Unauthenticated / PermissionDenied | 3 |
| NotFound | 4 |
| Conflict | 5 |
| Unavailable | 6 |

- 成功退出码为 0。上述非零值是项目约定，不是通用 CLI 标准。
- 默认用户错误信息输出到 stderr，格式为 `error[<CODE>]: <message>`；有关联标识时可以附带该标识。
- `--verbose` 可以增加经过脱敏的诊断信息，不授权输出凭据、令牌或其他受保护数据。

### TUI

- 在状态栏或弹窗展示安全文案；内部失败可以附带关联标识，引导用户查阅日志。
- 没有关联标识时省略该部分，不展示伪造的 `trace_id`。
- 交互式 TUI 正在控制终端时，日志不得写入其 stdout/stderr，应在入口配置文件或其他不会破坏界面的输出通道。

## 9. 错误码与元数据

- 格式为 `<MODULE>_<REASON>`，由全大写字母、数字和下划线组成；模块前缀在各契约所有者之间唯一。
- 每个操作错误码必须有唯一的静态描述符，至少记录 `code` 与 `kind`。错误类型从描述符取得分类和错误码，不维护独立的字符串及分类清单。
- 定义操作错误码的模块必须提供可枚举的描述符集合，由常量列表或生成代码实现；全局检查收集模块集合，而不是靠构造若干错误样本猜测全部错误码。
- 同一语义的多个错误实例可以共用描述符。转发已有契约时可以沿用其描述符，不重复注册该错误码。
- 错误码一经发布不可修改、不可复用。废弃时在代码元数据中保留并标注 deprecated，不要求保留已无用途的 Rust 变体。
- 不得保持错误码不变却悄然改变失败语义。调整已发布错误码的分类或协议映射属于兼容性变更，必须明确版本或迁移策略。
- 客户端依据错误码及正式定义的结构化字段处理，不解析 `message`、`Display` 或 `Debug`；文案可以改进或本地化。
- 代码元数据是实际错误码的唯一事实来源；需要清单时从代码生成，不在本文手写具体错误码。
- 唯一性检查必须覆盖可共同部署的模块及合法 feature 组合。插件注册时必须检查前缀和错误码冲突；未知插件错误不得直接采用未经校验的描述符。

## 10. 日志与诊断规范

- 对同一次向上传播的最终失败，由明确的责任边界记录一次。HTTP 中间件与 handler、任务入口与其调用方等必须选定记录方，避免重复记录同一失败。
- 中间层只负责保留原因与补充上下文，不在传播失败时逐层记录相同错误。
- 重试尝试、恢复事件和异步投递失败可以有独立观测记录，但必须与最终失败记录区分，并携带关联标识。
- 内部原因链不天然安全。日志和 verbose 输出均必须按敏感信息规则脱敏，不输出密码、令牌、密钥或未经允许的敏感业务数据。
- 使用结构化字段记录错误码、分类、关联标识、操作及脱敏后的原因链；保留足够信息排查，而不是承诺完整输出所有内部数据。
- 默认级别：未恢复的 `Internal` 为 `error`，未恢复的 `Unavailable` 为 `warn`，其余预期业务失败为 `info` 或 `debug`。预期取消、恢复中的尝试等按事件语义确定级别；告警应结合持续时间、频率和影响，不仅由分类决定。

## 11. 生命周期、事件与跨模块场景

- **启动失败**：缺少必需组件、无效必需配置等使运行条件不成立时，启动失败并返回非零退出码；可选组件失败是否允许降级由其生命周期契约决定。原因链保留到入口，展示和日志仍需脱敏。
- **异步通知事件**：处理器失败通常不回传为发布操作的业务失败；发布者仍需知道事件是否被接收或持久化。处理边界负责观测，并按投递契约重试或进入死信。
- **同步请求、事务参与或要求处理确认的事件**：必须定义失败传播、确认时机及事务语义，不能套用“处理器失败永不影响发布者”。
- **跨模块调用**：可以依赖接口公开的错误类型，不依赖内部表示。在进程内保留必要的结构化字段与原因链；跨进程序列化采用明确的错误协议，不序列化内部原因。
- **重试**：`Unavailable` 仅说明暂时不可用。是否重试还取决于操作幂等性、执行结果是否确定、重试预算、退避与取消状态；不得仅凭分类自动重试。具体策略属于调用方或基础设施策略，错误可以提供可信的等待时间等提示，不编码执行过的重试次数。

## 12. 禁止事项

- 禁止在业务模块和应用用例的公共操作 API 中使用 `Result<T, String>`、裸 `Box<dyn Error>` 或 `anyhow::Result` 替代语义错误契约。明确具有开放失败集合的底层扩展接口可以约定类型擦除载体，但必须文档化并满足所需的 `Send + Sync + 'static` 约束。
- 禁止在非测试代码中使用 `unwrap()`；`expect()` 仅用于有可验证不变量的场景，必须说明该不变量。外部输入、网络、磁盘或环境可变条件不属于“不可能失败”。
- 禁止在公共错误字段或转换签名中泄漏可替换的具体基础设施库类型。
- 禁止将诊断格式直接作为用户安全文案，或将敏感信息写入日志和 verbose 输出。
- 禁止用 `NotFound` 表达接口约定中的正常缺席；可选且可能失败的查询应返回 `Result<Option<T>, E>`。
- 禁止在补充上下文时无理由改变分类，或在传播同一失败时逐层重复记录日志。
- 禁止新增枚举所有业务模块变体的跨模块“全局大 Error enum”；共享的小型分类契约及诊断封装不属于该禁令。

## 13. 新增或修改错误时的检查清单

- [ ] 是否明确了操作失败、局部校验失败或正常缺席的区别？
- [ ] 是否按语义分类，而非因没有单独展示需求就归入 `Internal`？
- [ ] 新增细分变体是否有处理、诊断或契约上的需要？
- [ ] 业务字段是否结构化，原因链是否保留，公共 API 是否隐藏实现库？
- [ ] 需要应用转换的类型是否满足 `Error + Send + Sync + 'static`？
- [ ] 描述符是否来自可枚举元数据，映射是否穷尽，错误码是否唯一？
- [ ] 是否保持已发布错误码的语义，或明确了兼容性变更策略？
- [ ] 文案是否安全，补充上下文后是否保留分类、错误码与追踪关联？
- [ ] 是否选定最终日志的记录方，并检查诊断信息脱敏？
- [ ] 是否补充了契约相关测试，包括所影响的 feature、适配器或插件？

## 14. Lint 与测试

默认工作区配置：

```toml
[workspace.lints.clippy]
unwrap_used = "deny"
expect_used = "warn"
panic = "warn"
```

各 crate 继承：

```toml
[lints]
workspace = true
```

在工作区 `clippy.toml` 中明确允许测试使用断言式失败：

```toml
allow-unwrap-in-tests = true
allow-expect-in-tests = true
allow-panic-in-tests = true
```

- 默认 CI 对合法且可共同启用的 features 执行 `cargo clippy --workspace --all-targets --all-features -- -D warnings`。存在互斥 features 时，执行覆盖合法组合的矩阵，不要求构建无效组合。
- 有理由的生产代码 `expect` 或 `panic` 使用范围尽可能小的 lint 例外并说明不变量；不能全 crate 放宽规则。lint 不代替不变量审查，也不能证明所有 panic 都已消除。
- 使用的 Clippy 版本及检查矩阵必须在项目工具链或 CI 配置中明确；测试配置的覆盖范围以该版本行为为准。

测试要求：

- 操作错误：验证所有公开原因的描述符映射及所需线程安全约束。
- 错误元数据：验证格式、唯一性、废弃码保留，以及合法 feature / 插件组合的完整注册。
- 应用转换：验证分类与错误码保留、上下文不改变语义、原因链可追踪、关联标识不被重新生成。
- 安全展示：验证所有分类均不泄漏诊断载荷，尤其是 `Internal` 和含路径、凭据等数据的错误；日志与 verbose 同样验证脱敏。
- 适配器：验证每个分类的映射、固定响应结构、必要协议头及已文档化的特殊映射。依靠穷尽匹配检查新增分类，测试验证映射行为。
- 局部错误：验证解析或校验契约，不强制为它们增加分类与全局错误码测试。

## 15. 常见问题

**Q：什么时候新增变体，什么时候用 `Internal`？**
先判断失败语义，再决定细分程度。需要不同处理、诊断或稳定契约时新增变体；确实未知或无法合理分类的内部失败才使用 `Internal`。

**Q：给错误加 Context 后还能保留分类吗？**
必须保留。把上下文放入诊断原因或应用错误的诊断字段，不把所有原因重新包装为模块 `Internal`。

**Q：需要重试怎么办？**
按第 11 节判断操作是否可以安全重做，设置预算与退避，并尊重取消。`Unavailable` 不是自动重试许可。

**Q：值对象校验失败用什么？**
返回小型 struct 或 enum，不强制带内部失败变体。操作边界根据来源与用例语义转换；用户输入无效与持久化数据损坏不必归为同一分类。

**Q：新增业务模块需要改本文档吗？**
沿用现有契约时不需要。新增操作错误描述符、元数据集合和所需应用转换，并补充测试；新增分类或修改公开错误协议时必须同步修改规范。
