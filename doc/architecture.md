## 1. 当前是否可以开始架构设计

可以开始概要架构设计。核心产品范围已经足以识别 VFS、两类插件、访问入口和外围权限等职责。尚未确定的路径细节、插件执行模型和部署模式仍需明确；相关结构可以提出候选并做验证，不能悄然当作已批准方案。

建议同时维护需求、结构、运行场景和重要决策，通过小规模验证迭代。架构文档可以参考 arc42 的目标与约束、模块视图、运行视图、部署视图及决策记录等内容，按本项目规模裁剪。[arc42 模板](https://arc42.org/overview/)、[arc42 工作方法](https://arc42.org/method/)

本文记录逻辑边界及具体 crate 计划。asset-hub 与官方插件的项目归属已明确；crate 职责、依赖和验证要求见第 5～7 节。具体公共接口、进程数量及插件加载机制仍未确定。

已明确的项目边界：asset-hub 提供内核、公开契约、插件宿主、应用与访问入口；本地、S3、内存驱动及文本、MP4、game-hub 等官方资源插件放在独立项目中。官方插件不属于 asset-hub 的 workspace，其具体实现不进入 asset-hub 的生产依赖。选型方向见 TS-04；独立项目的建议名称与组织见第 7.3 节。

## 2. 架构设计推进方式

| 步骤 | 需要完成的工作 | 可审阅产物 |
|---|---|---|
| 1：确定本轮输入 | 确认当前里程碑的需求范围、关键质量目标与已明确技术方向，列出会影响结构的待决问题。 | 需求编号、质量场景和待决清单 |
| 2：定义系统上下文 | 明确各客户端、服务、插件开发者、身份/策略提供方和存储后端如何交互。 | 系统边界图与外部接口清单 |
| 3：定义模块职责 | 为每个候选模块说明负责什么、拥有哪些数据、公开什么能力、依赖谁。 | 模块说明和源码依赖关系 |
| 4：推演运行场景 | 逐步走通普通资源访问、game-hub 页面、CLI 插件动作和挂载变更。 | 调用流程或时序图 |
| 5：定义关键契约 | 明确公共输入输出、操作语义、资源生命周期、并发和能力限制；区分进程内接口与对外协议。 | 接口契约草案及关联需求 |
| 6：验证重大选择 | 用最小原型验证客户端插件贡献、插件交付形式和对象存储差异。 | 技术验证结果与 ADR |
| 7：形成开发切片 | 按完整场景组织任务，关联需求、契约和验收，逐步实现。 | 开发任务与验证计划 |

这些工作可以往返迭代。优先确定会改变模块边界的选择，无需先为所有内部函数或全部未来功能完成详细设计。

## 4. 系统上下文与部署问题

系统连接以下参与方：

- 使用者通过 Web、桌面、移动、CLI 或未来 TUI 访问产品。
- 管理者配置存储范围、挂载、插件及文件夹绑定。
- 第三方提供存储驱动或资源插件及其入口贡献。
- 外围身份与策略能力约束用户可执行的操作。
- 本地文件、S3、内存及未来后端提供实际资源。

**建议的首个验证形态**：一个应用服务配合多个客户端，通过统一的应用访问契约完成资源和插件业务操作。可优先用 HTTP 验证远程调用，再单独评估桌面或 CLI 是否需要嵌入本地服务。

该建议不等于已经选择远程 CLI，也不决定多实例部署、离线模式或插件进程模型。最终部署视图需明确各模块所在位置、状态保存位置、客户端连接与插件执行方式。

## 5. 候选模块与数据所有权

以下是跨项目的逻辑职责，不代表它们全部属于 asset-hub。具体所属项目与 crate 计划见第 5.3 和 7.3 节；一个 crate 不必对应一个进程或服务。

| 模块 | 负责的事情 | 拥有的概念/数据 | 公开能力 |
|---|---|---|---|
| VFS 核心 | 虚拟路径、目录组合、挂载解析与通用资源语义 | 虚拟位置、挂载语义、通用条目与操作模型 | 挂载及通用资源操作契约 |
| 存储驱动契约 | 定义后端配置接入、范围绑定、目录与字节操作、能力和保证 | 公开驱动模型与操作契约 | 驱动 SDK |
| 外部存储驱动实现 | 实现后端操作及所声明保证 | 后端专用配置、绑定资源和运行连接 | 驱动契约的实现 |
| 插件运行基础设施 | 插件产物发现、兼容检查、加载、执行与释放 | 安装定义、产物清单与执行句柄 | 各宿主可使用的插件运行能力 |
| 存储驱动宿主 | 注册已加载驱动、创建实例、管理实例生命周期 | 可用驱动声明与存储实例 | 实例创建与运行管理 |
| 应用用例 | 编排原生操作和资源插件业务操作，保持各入口的用例语义 | 用例请求、执行上下文、结果 | 入口可调用的应用能力 |
| 外围访问策略 | 身份与授权、资源及动作可见性、受控调用 | 用户/策略相关上下文 | 授权和受控资源访问边界 |
| 资源插件管理 | 发现与注册插件，管理目录绑定，选择和分派动作/视图 | 插件声明、绑定定义、配置引用 | 绑定、发现、选择与业务分派契约 |
| 外部资源插件业务实现 | 文本编辑、媒体操作、game-hub 等专用业务 | 插件自己的业务模型和所声明数据 | 插件动作及所需数据 |
| Dioxus 图形宿主 | Web、桌面、移动端各自接入插件页面、导航、动作和交互；共享适用实现 | 各平台图形状态、呈现与交互状态 | 各图形端的贡献接入契约 |
| CLI 宿主 | 用 clap 定义和解析命令，提供脚本输出和适用终端交互，接入 CLI 贡献 | 命令声明、调用与输出模型 | CLI 贡献接入契约 |
| HTTP 适配器 | 对外资源与插件调用协议、内容传输、必要的扩展接口 | 协议请求和响应 | HTTP 公共协议 |
| 状态保存与运行装配 | 保存各模块要求的配置/状态，选择实现并管理启动和释放 | 具体保存与组装机制 | 对应模块定义的保存和生命周期接口 |

资源插件业务数据的字段由插件定义，保存范围和访问由宿主契约约束。是否共用一个数据库、是否写入资源目录，以及具体驱动连接如何复用，均未决定。

### 5.2 实体实现约定

实体的 builder 构造采用 bon，字段访问器采用 getset，选型依据见 TS-03。实体所属模块仍需明确业务不变量、构造校验、可变性、公开 API 和验证场景；不由代码生成宏代替这些设计。

实体保留在其业务所属 crate 中；不设集中容纳所有实体的 common/models crate。只有确实跨边界共享的概念进入对应公开契约。生成的 builder 和访问器不能绕过已经约定的构造校验与状态变更规则。

### 5.3 asset-hub 的 crate 计划

使用 ah- 作为 crate 前缀。下表描述项目内主要依赖方向，不锁定全部第三方库或最终函数签名；公开类型需要的直接依赖在契约细化时补充。按开发切片创建这些 crate，不要求预先创建空项目。

| Crate | 职责与公开能力 | 项目内主要依赖 | 约束与验证重点 |
|---|---|---|---|
| ah-vfs-types | VirtualPath、MountId、资源条目、元信息、修订标识等基础类型 | 无 | 不包含身份、权限、插件业务或入口框架类型；路径经受校验的构造入口产生，不用本地 PathBuf 代替虚拟路径。 |
| ah-storage-api | 驱动 SDK：声明、配置接入、实例创建、能力、后端相对位置及目录/字节操作 | ah-vfs-types | 不依赖驱动或 VFS 实现；驱动只处理绑定范围内位置，不解析全局虚拟路径；不公开具体后端 SDK 类型。 |
| ah-vfs | 根挂载、挂载表、路径解析、目录组合及通用资源操作 | ah-storage-api、ah-vfs-types | 不依赖插件加载器、具体驱动、资源插件、权限或 UI；验证根约束、路径段匹配、目录规则与操作期间挂载视图。 |
| ah-plugin-runtime | 插件产物发现、清单读取、兼容检查、加载、执行及生命周期 | 基础执行机制不要求依赖项目业务实现；具体桥接接口另行定义 | 不实现存储或资源业务；平台执行机制隔离在适配模块，不能把进程启动或本地加载能力带入浏览器公共 SDK。 |
| ah-storage-host | 已加载驱动的注册、能力查询、实例创建与生命周期管理 | ah-storage-api、ah-plugin-runtime | 不解析虚拟路径，不实现本地/S3/内存操作；把按公开契约创建的实例交给 VFS，验证实例身份和释放。 |
| ah-resource-api | 资源插件 SDK：插件声明、匹配条件、业务动作、ResourceAccess 与插件状态访问接口 | ah-vfs-types | 不依赖 VFS 实现、存储驱动、数据库、Dioxus 或 clap；公开受控能力，不公开原始 VFS 对象与后端凭据。 |
| ah-resource-host | 注册、兼容检查、资源匹配、目录绑定、动作发现、分派与生命周期 | ah-resource-api、ah-plugin-runtime | 不包含文本编辑、媒体播放或游戏管理业务，不按插件名称写专用分支；验证绑定和停用行为。 |
| ah-app | 统一应用用例，编排 VFS、存储宿主、资源宿主及外围策略 | ah-vfs、ah-storage-host、ah-resource-host 及相关公开契约 | 定义并注入策略接口，不依赖具体权限实现；不含路由、命令解析或页面代码；各入口和插件资源访问遵循同一用例语义。 |
| ah-protocol | 请求/响应 DTO、资源与动作描述、协议版本 | 按协议需要选择轻量契约；不依赖宿主实现 | 不携带驱动对象、内部运行句柄、Dioxus 组件或 clap 命令；内部模型变更不自动改变协议。 |
| ah-http | HTTP 路由、协议转换、上传下载及插件动作访问 | ah-app、ah-protocol | 不直接调用具体驱动，不在 handler 中复制业务规则；HTTP 框架类型保持在边界内。 |
| ah-client | 客户端资源与插件动作调用抽象、内容传输及协议适配 | ah-protocol | 公共客户端能力不依赖服务端实现、VFS 或驱动；远程/嵌入式方式见 D-12，不能在未决时默认锁定一种模式。 |
| ah-ui-api | Dioxus 图形插件 SDK：页面、导航、资源视图、交互和业务调用上下文 | ah-client 及适用协议类型 | 允许依赖 Dioxus，不引用服务端内部实现；声明 Web、桌面、移动的贡献和兼容范围。 |
| ah-ui | Dioxus 应用外壳、通用资源页面、图形插件宿主 | ah-ui-api、ah-client；加载适配按平台确定 | 三类图形平台分别保留插件定制；不包含具体插件页面，不硬编码插件名称；平台入口和适配先用内部模块/features 组织。 |
| ah-cli-api | CLI 插件 SDK：命令、参数映射、输出及终端交互贡献 | ah-client 及适用协议类型 | 允许依赖 clap，不依赖 Dioxus、VFS 或服务端实现；明确命名冲突和脚本输出契约。 |
| ah-cli | CLI 程序、原生命令、插件命令装配及输出 | ah-cli-api、ah-client | 使用 clap；业务操作通过统一调用能力执行；不把具体官方命令实现放入宿主。 |
| ah-state | 实现挂载定义、目录绑定和插件状态的保存接口 | ah-app、ah-resource-host、ah-resource-api 中所属保存接口 | 接口由数据所属模块定义，数据库/文件格式留在实现内部；不定义 game-hub 等插件的具体业务字段。 |
| ah-server | 服务端启动装配、配置、状态恢复、策略注入及 HTTP 启动 | 项目内应用、宿主、VFS、入口与基础设施 | 通过配置和公共注册机制加载外部插件；生产依赖不列入具体官方插件；入口不承担存储或资源业务。 |

### 5.4 关键接口的细化范围

下列名称表达接口责任，尚不是最终 Rust 签名：

- VFS：mount、update_mount、unmount、list_mounts；stat、list、open_read、write、create_directory、remove、move；解析并固定本次操作的挂载目标。
- 驱动 SDK：StorageDriver/StorageInstance、能力声明、后端范围和相对位置、目录分页及字节流操作。流接口、并发与资源释放保证需正式定义。
- 资源 SDK：ResourcePlugin 声明和业务调用、ResourceAccess 通用资源访问、PluginStateStore 按插件与绑定实例限定的状态访问。
- 应用：统一用例入口与可注入的 AccessPolicy 等策略接口。插件的 ResourceAccess 实现由应用/宿主提供，并执行同一外围策略。
- 图形 SDK：贡献注册、页面和导航接入、资源视图扩展或替换、业务动作调用及逐平台能力声明。
- CLI SDK：贡献注册、clap 命令树接入、参数到动作的映射、输出与终端交互。

VFS 通用内容传输使用有界流处理，不能为普通下载先缓冲整个文件。挂载解析按路径段匹配；一次操作固定挂载视图。驱动和插件不直接引用 VFS 私有状态；某种后端或资源类型不能成为内核专用分支。具体路径、目录遮蔽和跨挂载操作仍以 D-01～D-06 的确认结果为准。

## 6. 调用关系与源码依赖

### 6.1 候选调用视图

下图表达运行调用关系，不是源码依赖图，也不要求不同框框处于不同进程。

~~~mermaid
flowchart TD
    W[Dioxus Web / 桌面 / 移动] --> GH[各图形宿主与插件贡献]
    C[独立 CLI：clap] --> CH[CLI 宿主与插件贡献]
    GH --> API[应用访问契约]
    CH --> API
    API --> A[应用用例与外围策略]
    A --> R[资源插件业务功能]
    A --> G[受控资源访问]
    R --> G
    G --> V[VFS 核心]
    V --> D[存储驱动契约]
    L[本地 / S3 / 内存 / 第三方实现] -.实现.-> D
~~~

应用访问契约可以由 HTTP 或确认后的其他调用方式实现。资源插件调用受控资源访问时，不再次分派同一插件动作；这需要在运行契约中明确。

### 6.2 建议的源码依赖边界

- VFS 依赖其需要的公开驱动/状态接口，不依赖 Dioxus、CLI 命令类型或权限实现。
- 具体存储驱动实现公开驱动契约，后端专用类型保持在实现边界。
- 资源插件业务依赖公开宿主 SDK 和资源访问能力，不引用 VFS 私有实现。
- 图形贡献可依赖选定的图形契约和 Dioxus；CLI 贡献依赖 CLI 契约。两种依赖不进入 VFS 或纯插件业务契约。
- clap 的命令解析依赖保持在 CLI 边界；bon/getset 按所选实体实现使用，不承担入口适配或插件执行职责。
- 应用访问协议、插件动作协议与领域内部模型分别确定所有者，避免直接把内部状态当作跨端共享协议。

asset-hub 的生产依赖不包含具体官方或第三方插件，插件经加载/适配后按公开契约调用。具体函数签名和执行桥接仍需在契约设计时审阅；共享代码由实际复用需求驱动，不预设一个所有模块均依赖的通用大模块。

### 6.3 主要源码依赖方向

箭头表示源码依赖，不表示运行调用方向；SDK 依赖与插件运行协议需要分别设计。

~~~text
ah-vfs              -> ah-storage-api + ah-vfs-types
ah-storage-api      -> ah-vfs-types
ah-storage-host     -> ah-storage-api + ah-plugin-runtime
ah-resource-api     -> ah-vfs-types
ah-resource-host    -> ah-resource-api + ah-plugin-runtime
ah-app              -> ah-vfs + ah-storage-host + ah-resource-host

ah-http             -> ah-app + ah-protocol
ah-client           -> ah-protocol
ah-ui-api           -> ah-client + Dioxus
ah-ui               -> ah-ui-api + ah-client
ah-cli-api          -> ah-client + clap
ah-cli              -> ah-cli-api + ah-client
ah-state            -> 保存接口所属的项目内 crate
ah-server           -> 项目内应用、宿主、入口与基础设施

外部驱动            -> ah-storage-api + 适用基础类型
外部资源业务        -> ah-resource-api + 自身业务契约
外部图形贡献        -> ah-ui-api + 自身业务契约
外部 CLI 贡献       -> ah-cli-api + 自身业务契约
~~~

应用不依赖 ah-state 具体实现；保存接口的实现由启动装配注入。客户端 SDK 不依赖服务端应用实现；未来嵌入式调用需设计明确适配，不能私自引入 VFS 和驱动依赖。外部插件不得依赖 ah-vfs、ah-app、各 host 或 runtime 的私有实现。

## 7. 插件架构需要先明确的事情

### 7.1 分清两类插件和入口贡献

| 组成 | 承诺的能力 | 需要确定的契约 |
|---|---|---|
| 存储驱动插件 | 为挂载提供后端目录/字节操作与能力声明 | 配置、绑定、操作保证、注册和生命周期 |
| 资源插件业务 | 对文件或指定目录提供专用功能 | 适用范围、动作、参数、结果、受控资源访问和业务数据 |
| 图形贡献 | Web、桌面和移动宿主分别允许插件定制页面、导航、动作与交互 | 各平台贡献接入、业务调用、分发和宿主兼容性 |
| CLI 贡献 | 接入 clap 命令树，并提供命令输出/交互 | 命令发现、参数、业务调用、输出和命名冲突处理 |
| 未来 TUI 贡献 | 为终端界面提供视图与交互 | 宿主能力、视图接入与业务调用 |

同一资源插件可同时提供多个入口贡献，但不会因为采用 Dioxus 就自动得到 CLI 或 TUI 适配。

### 7.2 首先比较的交付方式

候选方式包括编译期集成、运行时模块、独立进程、WASM 或声明式贡献。它们可以按业务与呈现边界组合，不要求所有插件使用同一个执行机制。

比较时回答：第三方如何独立发布？安装是否需要重新构建宿主？可以定制多少交互？宿主升级后怎样检查兼容性？业务动作如何被不同入口调用？故障和资源释放如何界定？

当前不选择其中任何方式。候选的编译期集成也必须保持第 7.3 节的项目归属边界；组合构建放在独立发行/集成工程中，不能给 asset-hub 的生产 crate 增加具体插件依赖。尤其不能从“图形端用 Dioxus”推导出可直接加载任意第三方 Dioxus 组件。

### 7.3 独立官方插件项目

项目负责人已明确：官方驱动和资源插件不与 asset-hub 的 crate 同属一个项目或 workspace。以下是独立仓库/workspace 的组织计划；仓库名称不是汇总所有插件的同名大 crate，也不表示这些项目已经创建。

| 项目 | 所有权与内容 | 构建及发布边界 |
|---|---|---|
| asset-hub | 内核、公开契约、插件运行基础设施、宿主、应用、各入口及通用状态适配 | 项目内 crate 单独形成 workspace；可发布供插件依赖的 SDK/契约。 |
| ah-plugins-driver | 官方本地、S3、内存驱动及未来官方驱动 | 独立 workspace、版本与发布流程；插件各自提供产物和兼容声明。 |
| ah-plugins-resource | 官方文本、MP4、game-hub 等业务及其图形/CLI/未来入口贡献 | 独立 workspace、版本与发布流程；插件业务与入口贡献可分别交付。 |

Cargo workspace 成员由各自清单管理，共享本 workspace 的锁文件和构建管理。独立插件依赖公开 SDK 不等于成为 asset-hub 的 workspace 成员。[Cargo workspace 说明](https://doc.rust-lang.org/cargo/reference/workspaces.html)

官方驱动项目的建议结构：

~~~text
ah-plugins-driver/
  Cargo.toml                 # 该独立项目的 workspace
  crates/
    ah-driver-local/
    ah-driver-s3/
    ah-driver-memory/
~~~

三个驱动都实现 ah-storage-api，不依赖 ah-vfs 或 ah-app；运行适用的公共契约验证。后端配置、SDK 类型和平台差异保持在各自插件内，分别说明绑定范围、能力、操作保证与实例生命周期。

官方资源插件项目的建议结构：

~~~text
ah-plugins-resource/
  Cargo.toml                 # 该独立项目的 workspace
  plugins/
    text/
    mp4/
    game-hub/
      ah-gamehub-contract/
      ah-resource-gamehub/
      ah-gamehub-ui/
      ah-gamehub-cli/
~~~

| game-hub 示例 crate | 内容 | 允许的依赖边界 |
|---|---|---|
| ah-gamehub-contract | 条目模型、动作标识、请求/结果及版本 | 保持轻量，不依赖业务实现或入口框架。 |
| ah-resource-gamehub | 游戏管理业务及插件自己的数据 | ah-resource-api 与自身业务契约；通过受控资源和状态能力执行。 |
| ah-gamehub-ui | Web、桌面、移动端页面与交互 | ah-ui-api 与自身业务契约；不依赖服务端业务实现。 |
| ah-gamehub-cli | 命令、输出与终端交互 | ah-cli-api 与自身业务契约；调用与图形端相同的业务动作。 |

文本和 MP4 采用同一边界；小规模内部代码可以先以模块组织，再按独立发布或共享需要拆 crate。具体游戏管理动作与数据模型仍待 D-19 确认。

### 7.4 发布、安装和跨端贡献

- 官方插件与第三方插件使用同一公开契约和接入机制，不设置官方插件的内核专用通道。
- 发行包可以默认随附官方插件，宿主与插件仍是独立产物；默认随附不改变源码归属和 workspace 成员。
- 某种贡献若需随宿主重新构建，组合由独立发行/集成工程完成；具体构建和兼容机制待 D-08、D-10 验证。
- 服务端业务、图形贡献、CLI 贡献分别注册并检查兼容性。服务端安装业务插件不会自动产生三类图形端页面或 CLI 命令。
- 图形插件声明 Web、桌面、移动端支持范围；各已交付宿主分别验证页面、导航、动作和交互。CLI 验证命令接入、命名冲突、脚本输出与终端交互。
- 仓库和 crate 隔离先明确代码所有权；它们本身不提供动态加载、跨版本 ABI 或执行隔离保证。具体产物格式、调用桥接和运行保证仍需确认。

若首期使用进程内代码，应按可信扩展评估。受控 ResourceAccess 是接口访问边界；不可信代码的强隔离需要对应执行机制，不能仅由 SDK 接口声称已保证。

## 8. 关键运行场景

### 8.1 普通文件下载

入口请求 → 应用用例确定操作与资源 → 外围策略约束调用 → VFS 按确定的挂载解析结果执行 → 驱动提供字节 → 入口按传输契约交付。

需要验证：授权与执行资源一致，数据传输有明确生命周期，挂载变化不会让同一读取跳到其他后端。是否代理流或发放下载位置见 D-13。

### 8.2 打开 game-hub 文件夹

入口定位目录 → 应用确定目录绑定及可见插件功能 → 宿主选择本入口的适用贡献 → 图形页面或 CLI 输出调用插件业务 → 插件通过受控资源能力访问目录/文件 → 宿主呈现结果。

需要验证：目录绑定没有更改存储挂载，各端共享动作含义，插件数据和资源访问受外围策略约束；没有本入口适配时采用已约定行为。

### 8.3 保存文本或修改游戏信息

插件呈现收集输入 → 调用共享业务动作 → 应用/宿主检查操作范围 → 插件按所声明修订与数据契约处理 → 通过受控能力执行写入 → 入口呈现约定结果。

需要验证：版本冲突、无写入能力、取消与部分效果均按契约处理。具体信息模型、保存位置和保证仍由对应待决项确定。

### 8.4 挂载、绑定和插件变更

管理用例校验变更 → 生效明确版本的定义 → 后续发现和调用使用新定义 → 已开始的操作按生命周期契约完成或终止。

需要验证：根挂载约束、目录绑定继承、插件停用和已有流的资源释放；不能把三个不同生命周期混为一个操作。

### 8.5 外部驱动与根挂载启动

~~~text
读取宿主配置
  -> 从启动环境发现插件产物
  -> 检查并加载根挂载所需驱动
  -> 注册驱动并创建存储实例
  -> 建立 VFS 根挂载
  -> 恢复其他挂载与目录绑定所需插件和定义
  -> 按确认后的必要/可选组件策略启动访问入口
~~~

插件安装定义与启动发现来源必须独立于尚未建立的 VFS。根驱动缺失或不兼容时不能进入正常服务，也不能用宿主内置内存驱动替代配置。根定义存在而后端暂时不可用、可选插件不可用的处理仍由 D-15 确认；该顺序不预先决定全部降级策略。

挂载定义恢复不等于内存文件数据恢复。存储实例、资源插件执行与文件夹绑定各自遵守生命周期契约；依赖未就绪时不得对外呈现为已可用。

### 8.6 game-hub 跨入口调用

~~~text
外部 Dioxus 页面或 CLI 命令贡献
  -> ah-client 的统一调用能力
  -> 确认后的传输/调用适配（HTTP 实现对应 ah-http）
  -> ah-app 检查插件动作并建立受控上下文
  -> ah-resource-host 分派
  -> 外部 ah-resource-gamehub 执行业务
  -> 受控资源/状态接口
  -> ah-vfs 或状态适配执行
~~~

图形和 CLI 贡献不引用服务端业务实现。动作检查与插件随后发起的资源操作各自遵循外围策略；受控资源调用直接进入原生资源能力，不再次分派同一资源插件动作。

## 10. 进入开发前的建议输出

针对当前开发切片，建议具备：已确认的需求与预期、可解释的模块职责与数据所有权、源码依赖关系、关键运行流程、必要公共契约，以及影响实现的决策记录。

建议按以下切片推进，插件执行模型验证要尽早进行：

1. 用测试替身验证 ah-vfs-types、ah-storage-api、ah-vfs 的根挂载和基本资源行为；同期开立独立驱动项目，验证外部内存驱动的最小接入。
2. 走通外部根驱动加载 → 根挂载 → 目录查询 → 应用访问；逐步接入 HTTP 与 CLI，运行方式以确认后的契约为准。
3. 在独立资源插件项目验证 game-hub 目录绑定、共享业务动作及 Dioxus/CLI 贡献，尽早记录需要重新构建或平台适配的部分。
4. 完成本地与 S3 驱动的适用契约验证，再扩大持久化和已确认的外围策略；图形客户端按交付平台逐项验证插件定制。

这些是开发顺序建议，不改变首版范围或自动确认未决行为。

### 10.1 AI 实现任务的边界

- 每个任务写明目标 crate、关联需求、允许依赖、公共契约、验收场景和未决问题。
- 公共接口、依赖方向和操作保证是审阅边界；AI 可以实现私有细节，改变这些边界时必须同时更新设计、任务与关联验收，不能用实现便利性代替需求选择。
- 新增工作区 crate 或跨项目依赖须说明职责和所有权；具体插件不能作为 asset-hub 普通成员或生产依赖加入。
- SDK 保持对独立插件开发者可用，插件只依赖公开契约；宿主不能通过插件名称、类型白名单或专用业务分支补足契约缺陷。
- 实体按所属模块组织，使用 bon/getset 仍遵守已约定的不变量。平台与后端依赖留在对应适配或插件实现中。

### 10.2 验证与发布职责

| 所属项目/边界 | 应提供的验证证据 |
|---|---|
| asset-hub 内核 | 使用测试专用替身验证路径、根挂载、目录组合、挂载变更、流生命周期与通用操作；替身不作为生产内置驱动发布。 |
| 官方及第三方驱动项目 | 运行适用公共契约检查与后端专用案例，声明范围、能力和保证，不要求后端满足未声明语义。 |
| 资源插件项目 | 验证匹配、绑定、业务动作、受控访问、状态范围及各入口贡献，不依赖宿主私有实现。 |
| 各客户端宿主 | 验证贡献发现、兼容性、命名冲突与约定降级；Web、桌面、移动端分别验证图形定制，CLI 验证脚本和交互行为。 |
| 跨项目集成工程或 CI | 组合明确版本的宿主和外部插件，验证独立发布、根启动、文件操作及 game-hub 跨端动作；不把插件源码纳入 asset-hub workspace。 |

可复用契约检查由公开测试支持提供，具体是否新增 ah-testkit 在需要共享时决定。单元验证、插件验证与集成验证分工明确，原型通过不代替发布验收。
