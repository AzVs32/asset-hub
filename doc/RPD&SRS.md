## 第一部分：PRD — 产品需求

## 1. 产品背景与定位

### 1.1 要解决的问题

不同存储后端具有不同的命名、目录和访问方式。使用者需要通过统一的虚拟目录组织、访问和管理这些资源；开发者需要在统一资源能力上增加文本编辑、媒体播放或文件夹专用应用，并为不同访问入口提供适用的呈现和交互。

产品定位为：**以 VFS 为内核，统一多种存储，并通过插件扩展文件处理、文件夹应用及各访问入口的呈现与交互的平台。**

### 1.2 产品价值

1. **统一资源入口**：通过虚拟路径定位资源，降低使用者对后端差异的关注。
2. **可扩展存储接入**：新增驱动能复用既有挂载、访问和入口能力。
3. **可扩展资源功能**：通过文件类型插件增加阅读、编辑、播放，通过文件夹绑定创建 game-hub 等专用应用。
4. **可定制访问方式**：HTTP API、HTTP 前端、CLI 和未来入口共享业务能力，各入口同时提供插件扩展机制。
5. **职责分离**：VFS 提供资源能力，外围系统负责用户身份与访问策略。

### 1.3 根目录与层级路径

已明确的目录结构含义只有：从根目录开始，通过层级路径组织资源；根目录必须挂载。Linux/POSIX 兼容性及其文件系统语义与本产品无关，不能由“类似 Linux”推导出额外要求。

路径处理、挂载解析、目录组合和文件操作的语义均由本产品独立定义。对象存储的差异通过明确的 VFS 语义和驱动能力表达。

## 5. 核心使用场景

### UC-01：建立虚拟目录

管理者安装并配置根挂载所需驱动插件，宿主接入驱动并创建存储实例后建立根挂载；再将本地目录、S3 的存储范围和内存实例分别挂载到不同路径。使用者浏览根目录，定位并访问各挂载中的资源。

### UC-02：通过多个入口管理文件

使用者通过 HTTP 查询文件并下载，通过 CLI 查询同一路径。删除或移动操作应当具有一致的业务语义；入口承担协议和交互，同时支持插件定制适用范围内的命令、输出、页面和资源动作。

### UC-03：阅读和修改文本

使用者打开 txt、c 或 rs 文件。适用的文本插件通过受控的资源访问能力取得原始内容，可为 Web、桌面、移动端提供阅读/编辑页面，为 CLI 或未来 TUI 提供对应输出和交互；保存操作通过通用写入能力完成。插件无法因为使用了“编辑”动作而绕过外围写入权限。

### UC-04：播放 MP4

使用者选择 MP4 的播放动作。插件与宿主协作获得内容和播放所需信息。VFS 仍处理字节资源，不承担 MP4 解码。定位播放所需的范围读取能力和宿主兼容条件见 SRS。

### UC-05：将指定文件夹设置为 game-hub

使用者将某个虚拟文件夹（例如 /games）显式绑定为 game-hub。该目录取得插件提供的游戏管理功能；访问目录时，可使用插件提供的专用页面、输出和交互。该绑定与文件夹原有存储驱动和挂载位置分别管理，不要求把它重新挂载为某种专用存储。

game-hub 可为 Web、桌面、移动端提供游戏管理页面，为 CLI 提供游戏管理命令与输出，为未来 TUI 提供对应界面。各客户端可以有适合其平台的布局和交互，但都必须允许插件定制。具体游戏条目、信息编辑和页面布局是参考插件的待确认需求，不据此默认加入游戏下载、启动、安装或平台账号集成。

文件夹插件使用统一资源访问能力，不自行改变挂载拓扑或替换 VFS 的路径解析规则。子目录是否继承绑定、文件夹移动后绑定如何处理均待决。

### UC-06：第三方接入存储

第三方开发者实现公开驱动契约，声明能力和兼容版本，提供配置与验证材料。系统识别并注册该驱动后，其挂载能被既有入口访问。

### UC-07：施加访问策略

外围系统识别调用者并执行策略判断。拒绝的资源操作不会进入执行阶段；被允许的操作进入 VFS。直接测试 VFS 时不需要用户数据库、角色系统或策略服务。

### UC-08：同一插件定制不同访问入口

开发者为资源插件提供各入口适配。Web、桌面、移动端分别使用插件提供的页面和交互，CLI 使用插件命令和输出，TUI 使用插件界面；HTTP API 暴露该插件的服务侧功能和数据。不同入口可以采用不同交互形式，但同一业务动作具有一致含义。共享图形界面技术不意味着插件自动兼容所有平台，需声明并验证适配范围。

任一新入口在接入产品时，都需要说明插件怎样贡献功能和呈现。插件可声明支持的入口及能力，产品不要求所有插件自动具备所有入口的同一界面。

## 6. 两类插件与宿主边界

| 类型 | 提供的能力 | 作用范围 |
|---|---|---|
| 存储驱动插件 | 接入存储、绑定存储范围、提供字节和目录操作 | 存储适配边界 |
| 资源插件 | 文件匹配或显式文件夹绑定、专用业务动作，以及各入口的页面/命令/输出/交互贡献 | 文件处理、文件夹应用与入口定制边界 |
| 访问入口/宿主 | 协议和基础交互，接入插件贡献并展示或执行适用的功能 | HTTP API、HTTP 前端、CLI、未来 TUI 及其他入口 |

主项目提供公开契约、宿主、应用与入口；官方具体驱动、资源业务及其入口贡献均在独立插件项目中维护，与第三方插件使用同一接入机制。默认发行包可以随附这些独立产物，不改变项目归属。具体仓库、crate 与生产依赖边界见技术选型 TS-04 和架构第 5～7 节，本文不重复维护包结构。

资源插件的服务侧功能和入口专用呈现需要分别描述，并能协作使用同一资源与业务能力。以下定制目标已明确；使用共享界面描述、入口专用代码或其他机制属于后续架构决策。

| 入口 | 必须具备的插件扩展空间 | game-hub 的示例贡献，具体功能待确认 |
|---|---|---|
| HTTP API | 注册或暴露插件动作、数据和必要接口契约，使客户端可以调用插件功能 | 游戏条目查询与管理动作 |
| Web | 定制适用资源的页面、导航、展示和交互；允许扩展或替换默认资源视图 | 游戏管理页面、条目详情和信息编辑 |
| 桌面 | 定制适用资源的页面、导航、展示和交互；明确桌面平台适配范围 | 桌面游戏管理页面与对应交互 |
| 移动端 | 定制适用资源的页面、导航、展示和交互；明确移动平台适配范围 | 适配移动端布局和交互的游戏管理页面 |
| CLI | 定制命令或操作入口、输出组织和适用的终端交互 | 游戏列表、详情和管理命令 |
| TUI | 在该入口实现时支持定制视图、导航、输出和交互 | 游戏列表、详情视图和管理操作 |
| 未来其他入口 | 明确自己的插件贡献契约，不能只提供无法扩展的原生功能 | 按宿主能力提供适用形式 |

每个入口都提供扩展机制，但各插件可以选择支持哪些入口。未适配某插件的入口应按明确规则呈现通用资源或能力限制。HTTP 前端页面扩展是产品目标，完整 Web 管理界面的首版范围仍可裁剪。

VFS 必须允许通用字节读取和写入与资源插件分离。文件扩展名匹配、文本解释、媒体解码、编辑界面不得成为 VFS 的内置特殊分支。

## 8. 系统范围与逻辑边界

以下是职责关系示意，不指定物理部署、进程数量或源代码组织。

~~~mermaid
flowchart TD
    H[HTTP API] --> A[应用与外围访问策略]
    H -.接口扩展.-> E[各入口的插件扩展]
    W[Web / 桌面 / 移动端插件宿主] --> E
    C[CLI 宿主] --> E
    T[未来 TUI 或其他宿主] -.-> E
    E --> A
    E --> P[外部资源插件：业务功能与入口贡献]
    A --> V[VFS 内核]
    P --> G[受控资源访问]
    G --> A
    V --> D[存储驱动契约]
    L[外部本地驱动插件] -.实现.-> D
    S[外部 S3 驱动插件] -.实现.-> D
    M[外部内存驱动插件] -.实现.-> D
    X[第三方驱动] -.实现.-> D
~~~

- VFS 负责命名空间、挂载解析和通用资源行为，不识别终端用户身份与权限规则。
- 存储驱动负责适配后端及其范围约束，不解释资源插件动作。
- 应用与外围策略负责用例编排及用户访问决策，具体模块划分属于后续架构设计。
- 资源插件通过宿主提供的资源访问能力操作资源，不获得绕过策略的存储凭据。
- 各入口提供插件扩展契约；插件业务能力、文件夹绑定和入口专用呈现独立于 VFS 的存储行为。
- 图中回到应用边界的插件资源调用不再次触发同一插件动作；具体调用流程需在模块契约中说明，避免递归分派。

## 9. 术语与概念数据模型

| 术语 | 定义 |
|---|---|
| 虚拟路径 | 统一命名空间中的资源位置，不是宿主操作系统路径或 S3 对象键。 |
| 根挂载 | 挂载点为 / 的有效挂载，为 VFS 命名空间提供根。 |
| 挂载定义 | 将虚拟路径与驱动实例及其存储范围关联的配置。 |
| 驱动类型 | 某类存储实现的标识，例如本地、S3、内存。 |
| 驱动实例 | 含连接配置和后端范围的具体运行实例；同类型可有多个实例。 |
| 驱动内路径 | 挂载解析后，位于已绑定存储范围内的相对资源位置。 |
| 资源条目 | 可列出或查询的文件或目录及其元数据。 |
| 合成目录 | 为形成虚拟目录树而产生、不要求后端存在实体的目录。 |
| 驱动能力 | 技术上支持的操作和保证，例如读取、写入、范围读取、条件写入、原子移动。 |
| 插件动作 | 插件提供的资源使用或应用功能，例如阅读、编辑、播放、游戏条目管理。 |
| 文件夹绑定 | 将指定虚拟目录与资源插件及其配置关联，例如 /games 绑定为 game-hub；与存储挂载是不同概念。 |
| 入口贡献 | 插件针对入口提供的接口动作、页面、命令、输出或交互；具体描述和执行机制待设计。 |
| 插件宿主 | 发现、调用或呈现插件贡献，并管理其受控资源访问与生命周期的组件。 |
| 内容修订标识 | 用于识别内容版本的可选不透明值；不假定不同后端使用相同格式。 |

**建议的概念字段**：挂载至少具有标识、虚拟挂载点、驱动类型、后端范围、配置引用及启用状态；资源至少具有虚拟位置、名称和文件/目录类型，文件大小、修改时间、内容类型和修订标识允许按契约缺省。具体 DTO 和存储模型不在本文冻结。

路径是否是长期稳定的资源身份、移动后的引用如何处理，以及实例与挂载的共享关系见待决项。文件夹插件绑定、插件业务数据和存储挂载分别建模，其持久化与生命周期规则见 D-18、D-19。

### 10.8 权限系统与 VFS 解耦

| 编号 | 要求 | 状态 | 优先级 |
|---|---|---|---|
| FR-AUTH-01 | 权限系统是产品必要能力，但 VFS 不依赖用户、角色、ACL 或策略服务，也不根据终端用户身份判断操作是否允许。 | 已明确 | P0 |
| FR-AUTH-02 | 系统提供明确的外围授权位置，能够约束入口与插件发起的资源操作。认证、策略求值和最终用户权限信息在 VFS 外部处理。 | 建议 | P0 |
| FR-AUTH-03 | 授权基于与实际执行一致的规范资源位置及操作；移动涉及源与目标，递归操作涉及其覆盖范围。路径转换与挂载变化不能让授权对象和执行对象产生歧义。 | 建议 | P0 |
| FR-AUTH-04 | 目录条目、插件业务数据和动作的可见性，资源读取/修改及挂载管理分别需要策略要求；不同页面和输出遵守同一外围权限边界。具体规则与用户模型在独立权限规格中定义。 | 建议，见 D-14 | P0 |
| FR-AUTH-05 | VFS 和驱动的绑定范围约束仍需成立。后端凭据、后端自身拒绝访问及插件信任控制不同于终端用户权限，不因解耦而被忽略。 | 建议 | P0 |
| FR-AUTH-06 | 建议在启用权限管理的产品运行模式中，缺失必要策略或授权执行失败时拒绝相关外部操作。纯 VFS 测试无需初始化权限系统。首版运行模式需确认。 | 建议，见 D-14 | P0 |

“VFS 不关注权限”不意味着所有外部访问都允许。权限解耦要求职责和依赖分离，而不预先指定 IoC 或 AOP 的具体实现。

|---|---|---|---|

| FR-RUN-02 | 支持查询挂载、驱动与插件的声明及运行状态。查询声明不应依赖后端此刻健康，不得泄露凭据。 | 建议 | P0 |
| FR-RUN-03 | 失败应保留可识别的语义，并区分面向调用方的信息与内部诊断。错误分类、错误码、HTTP/CLI 映射和结构需为新项目单独设计，本文不继承现有规则。 | 建议 | P0 |
| FR-RUN-04 | 取消、超时、后端故障和插件失败具有明确的资源释放与结果语义。不可仅因为暂时故障就自动重做可能已生效的写操作。 | 建议 | P0 |

## 11. 非功能需求

所有数值是用于讨论的候选验证目标，不是已承诺 SLA。应在技术验证后确认测试环境、数据集、阈值与允许偏差。

| 编号 | 要求 | 初步验证方法/候选目标 | 状态 |
|---|---|---|---|
| NFR-01 | 核心文件传输采用有界资源使用，不因文件总大小线性增加内存。 | 单流传输至少 1 GiB 文件，候选目标为相对空闲基线额外内存不超过 64 MiB；区分插件缓冲、驱动缓冲与内存后端本身的数据占用。 | 建议 |
| NFR-02 | 大目录查询有分页、游标或等价的资源控制方式；同时说明顺序、挂载条目合成及并发变化影响。 | 使用至少 10 万条目的数据集；确认分页无重复、不会静默丢失挂载条目。分页范围和一致性等级待决。 | 建议，见 D-16 |
| NFR-03 | 多请求和挂载变更下保持公开不变量，不声称对所有后端提供全局内容快照。 | 并发列举、读写和挂载变更；验证操作不会中途切换后端，冲突按契约处理。 | 建议 |
| NFR-04 | 驱动故障的影响范围可界定，健康挂载可独立访问；插件执行的超时与失败影响需契约化。 | 注入一个后端故障，验证其他挂载仍可访问。进程内插件崩溃的隔离保证取决于 D-08 的选择。 | 建议 |
| NFR-05 | 外部凭据和敏感诊断不进入普通资源结果、插件匹配元数据或默认展示。 | 含凭据的失败输入与配置查询；检查普通输出和诊断脱敏。 | 建议 |
| NFR-06 | 新驱动、新资源插件及其各入口贡献可通过公开契约扩展，不要求 VFS 增加专用分支或各宿主硬编码插件名称。 | 接入独立示例驱动和 game-hub 等参考插件，检查 VFS 边界及各宿主贡献接入。 | 建议 |
| NFR-07 | 公开契约有版本与兼容性声明；破坏性变更可被识别、记录并验证。 | 用不兼容版本测试拒绝行为，用受支持版本运行契约检查。具体兼容周期待决。 | 建议 |
| NFR-08 | VFS、驱动、应用策略和入口能够分别测试；端到端测试覆盖跨边界行为。 | VFS 不初始化用户系统；驱动共享适用测试；入口运行同一业务场景。 | 建议 |
| NFR-09 | 操作结果与诊断可关联，能定位涉及的挂载、操作和插件；不得承诺完整公开内部原因。 | 验证关联标识和诊断记录，审查跨边界传播；具体观测结构后续设计。 | 建议 |
| NFR-10 | 内存存储、上传缓冲、编辑内容和插件执行具有可配置资源限制。 | 超过容量/预算时产生定义的失败并释放资源，不以进程崩溃作为正常处理方式。具体上限待决。 | 建议 |

操作延迟、吞吐量、并发数、部署操作系统和多实例服务目标当前没有数值基线。后端网络耗时应与 VFS 自身开销区分后评估。

| AT-32 | 在独立官方插件项目中构建三个初期驱动和参考资源插件及其入口贡献，仅通过公开契约接入明确版本的宿主。检查主项目 workspace 与生产依赖不含具体插件；默认随附或组合发行不改变归属，也无需核心专用分支。 | FR-SP-06、FR-CP-16、FR-DRV-01、NFR-06、NFR-07 |

每条功能与非功能需求至少关联一个验收场景，但一行场景不代表其全部边界案例已经穷尽。更细的模块测试和驱动专用测试应在契约确定后补充。最终发布验收应逐项覆盖已确认需求及其边界条件。

### 14.1 建立第一版需求基线
