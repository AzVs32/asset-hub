## 1. 本文的职责

本文记录技术方向、适用范围、选择理由和验证事项。产品能力继续由 PRD/SRS 定义；具体模块、依赖与运行流程由架构文档描述。

“方向已明确”表示项目负责人指定当前评估和设计的路线，不代表原型已经验证成功，也不锁定所有依赖或部署方案。影响公共契约的重要选择，后续可以形成单独的 ADR，记录状态、理由、代价和变更。

## 2. TS-01：Dioxus 用于 Web、桌面与移动端

### 2.1 当前方向

- Web 图形前端采用 Dioxus。
- 桌面图形客户端采用 Dioxus。
- 移动端图形客户端采用 Dioxus。
- Web、桌面和移动端每一类宿主都必须保留插件定制能力，允许插件在适用资源范围内贡献或定制页面、导航、动作与交互。
- 三类客户端评估共享业务调用、状态和适用组件；平台专用交互按实际需求适配。

方向来源：项目负责人本次明确提出的选择。各端的交付顺序、目标操作系统、最低版本和具体 Dioxus 版本仍待确认。

### 2.2 选择意图与适用边界

期望在图形客户端间复用实现和插件呈现方式，降低重复开发。复用比例与平台差异需要通过原型验证，不承诺全部界面无需适配。

Dioxus 官方支持 Web、桌面和移动平台，同时说明平台特性和依赖存在差异；这支持将其作为三类图形客户端的评估方向。[Dioxus 平台说明](https://dioxuslabs.com/learn/0.7/guides/platforms/)

本选择只确定图形客户端方向。VFS、存储驱动、服务端应用、权限系统和持久化技术各自评估，不由图形框架的选择自动决定。

### 2.3 需要验证的事项

| 验证项 | 完成证据 |
|---|---|
| 普通资源页面 | Web 能列举虚拟目录、打开资源并调用应用动作。 |
| 文件夹插件页面 | /games 绑定 game-hub 后，Web、桌面、移动各已交付宿主分别验证插件页面、导航、动作与交互的接入。 |
| 多端复用 | 在三类图形端验证插件适配和同一业务动作，记录共享代码与平台差异；复用策略不能取消任一图形端的插件扩展空间。 |
| 插件交付 | 说明插件如何分发和接入宿主，是否需要重新构建，如何声明宿主兼容版本。 |
| 媒体功能 | 选定参考 MP4 与数据通路在目标宿主中满足约定的播放行为。 |

选择 Dioxus 并不等于已经选择动态组件加载、通用 UI 描述或前端插件包格式。这些需要单独验证和决策。

## 3. TS-02：CLI 使用 clap 独立实现

### 3.1 当前方向

CLI 使用 Rust 和 clap 实现命令定义、参数解析与帮助信息；输出和适用的终端交互由 CLI 宿主实现，不由 Dioxus 承担 CLI 呈现。

clap 是已选的命令行库。具体版本、其他终端依赖、命令协议和远程/嵌入式运行模式当前未选定。clap 提供 derive 与命令构建 API，具体组合方式需配合插件贡献契约验证。[clap 官方文档](https://docs.rs/clap/latest/clap/)

### 3.2 与其他入口的关系

- CLI 和图形客户端复用同一组应用能力和业务语义。
- CLI 必须具有插件贡献机制，允许插件增加或定制命令、输出和交互。
- clap 命令树需要接入插件贡献；选用 clap 不改变插件命令发现、命名冲突和调用分派的设计要求。
- 同一资源插件可以有 Dioxus 图形适配和独立 CLI 适配，适配层不重复定义相互冲突的业务规则。
- CLI 的实现方式不改变 VFS 与权限系统解耦的要求。

### 3.3 需要验证的事项

验证 game-hub 的命令贡献能够进入 clap 命令树，其输出和至少一个管理动作与图形入口调用相同业务功能；同时明确脚本输出与交互输出的差异，以及插件命令的发现和命名规则。

## 4. TS-03：实体使用 bon 与 getset

### 4.1 当前选择

项目实体以 Rust 结构体表达，其 builder 构造采用 bon，字段访问器采用 getset。该选择来源于项目负责人的明确要求；具体版本在建立实现工具链时确定。

| 库 | 本项目中的用途 | 依据 |
|---|---|---|
| bon | 生成实体的 builder 构造接口，减少重复的构造代码。 | [bon Builder 官方文档](https://docs.rs/bon/latest/bon/derive.Builder.html) |
| getset | 生成按实体契约选择的 getter、setter 或其他字段访问器。 | [getset 官方文档](https://docs.rs/getset/latest/getset/) |

### 4.2 与实体设计的关系

这些库承担构造和访问器生成；实体的业务含义、构造校验、字段可变性、访问器可见性以及生成接口是否进入公共 API，仍需在实体契约中明确。

getset 面向基本字段访问器；需要自定义行为的访问或修改操作由实体方法表达，其余适用字段仍使用 getset。该分工不预先决定哪些字段允许公开修改。[getset 的适用范围](https://docs.rs/getset/latest/getset/)

实体库选择与插件 ABI、协议 DTO、持久化模型分别设计，不自动要求第三方插件暴露宏生成的 builder 类型。

## 5. TS-04：主项目与官方插件独立组织

### 5.1 当前方向

项目负责人已明确：asset-hub 提供内核、公开契约、插件宿主、应用和访问入口；本地、S3、内存驱动以及官方资源插件采用外部插件形式，不属于 asset-hub 的 workspace。

官方插件独立组织为 ah-plugins-driver、ah-plugins-resource 两个项目，各自管理 workspace、版本、构建与发布。项目名称用于仓库/workspace，不要求创建汇总所有插件的同名 crate。具体 crate 职责和结构统一维护在 [架构草案第 5～7 节](architecture.md)。

### 5.2 已明确的边界

- 官方与第三方插件使用同一公开契约和宿主接入机制；官方实现不获得内核专用分支或类型白名单。
- 插件依赖 asset-hub 发布的 SDK/契约，不引用 VFS、应用或宿主的私有实现。asset-hub 的生产依赖不列入具体插件，包括官方实现。
- 插件业务和 Web/桌面/移动端图形贡献、CLI 贡献均放在独立插件项目中；主项目提供通用 SDK 与宿主。
- 发行包可以默认随附官方插件，独立产物和源码归属保持不变。若需要组合编译，由独立发行/集成工程负责，不把具体插件加入主项目生产依赖。

依赖公开 SDK 与加入同一个 workspace 是不同关系；Cargo 由各 workspace 清单管理成员，共享本 workspace 的锁文件及构建配置。[Cargo workspace 说明](https://doc.rust-lang.org/cargo/reference/workspaces.html)

### 5.3 尚需验证的机制

独立仓库和 crate 不能直接证明动态加载、跨版本 ABI 或执行隔离能力。插件产物格式、分发安装、SDK 版本兼容、调用桥接、图形贡献加载方式和可信范围仍需验证。服务端、CLI、Web、桌面和移动宿主可以有不同执行或加载适配，但都必须保留插件扩展空间。

用独立驱动项目验证根插件先于 VFS 根挂载就绪；用独立 game-hub 验证业务与图形/CLI 贡献的分别注册和共享调用。完整计划与验收关联见架构草案第 8～10 节。

## 7. 最小技术验证建议

先由独立官方驱动项目提供最小内存驱动产物，验证宿主可从 VFS 之外发现并接入、创建实例、建立根挂载。缺失或不兼容的根驱动不能由内置实现替代。具体产物形式由候选机制原型比较，不在此处锁定。

再使用独立官方资源插件项目中的同一个 game-hub 完成：

1. 独立的业务数据与动作，例如游戏条目查询和信息修改；具体功能以确认后的参考需求为准。
2. Dioxus Web 中接入插件页面与交互。
3. 使用 clap 接入 CLI 插件命令与输出，调用同一业务动作。
4. 在选定桌面与移动目标分别验证图形插件定制能力、适配和平台差异。
5. 检查业务、图形和 CLI 贡献分别注册后的兼容关系，记录插件接入步骤、宿主修改范围、构建方式和兼容边界。
6. 验证 asset-hub 与插件可独立构建和发布；组合发行不改变 workspace 归属，主项目生产依赖不包含具体插件。

这是验证计划，不表示已经执行或选择了插件加载模型。结论进入技术验证报告和后续 ADR，再更新架构草案。
